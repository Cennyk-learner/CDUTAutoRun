# 校园跑小程序漏洞分析与修复建议

> 本文档面向校方相关老师 / 技术负责人，目的是说明问题根因并给出可落地的修复方案。
> 所有个人敏感信息已脱敏，本文仅用于安全研究与协助修复，详见仓库根目录《安全声明.md》。

## 一、问题概述

"校园跑 / 体育打卡"微信小程序（后端 `clty.cdut.edu.cn`）允许用户在**完全没有真实运动**
的情况下，通过脚本向服务端上报一段伪造的 GPS 轨迹，最终被系统记录为**一次合规、达标的
校园跑**（里程达标、配速落在规则区间、时间窗合法）。

整个利用链不需要逆向任何加密签名，只需要：

1. 从微信小程序进程内存中提取出会话凭证 `au`；
2. 用普通 HTTP 客户端，按服务端规则构造 GPS 点位、步数、配速并上报。

## 二、利用链与根因

### 根因 1：会话凭证 `au` 明文长期驻留、可被提取并任意重放

- 小程序运行时，`au`（服务端真正校验身份的字段）以明文形式存在于 `WeChatAppEx.exe`
  进程内存中，可被本地内存扫描脚本直接读出。
- 该 `au` **没有与设备 / 会话 / IP 强绑定，也没有足够短的有效期**，因此可以被复制到
  任意外部 HTTP 客户端中长期重放，服务端无法区分"真实小程序"与"脚本"。

### 根因 2：运动数据完全由客户端上报，服务端缺乏独立校验（核心问题）

服务端的判定几乎完全建立在"信任客户端上报的数据"之上：

- **里程 / 配速 / 步数**均由客户端 `/coll/collect/sport/gps`、`/api/applet/soprt/end`
  等接口提交，服务端只校验它们是否落在规则区间（`milage` / `timeRule` / `speedRule`），
  而这些数值都能在客户端任意构造。
- **地理围栏只做了"点是否在多边形内"的几何判断**：脚本把围栏多边形向中心等比内缩，
  就能生成一条"始终在范围内"的环形轨迹，绕过围栏限制。
- **打卡照片没有真实性校验**：上传一张程序生成的噪声 PNG 即可通过，不要求来自真实摄像头。

### 根因 3：缺乏请求完整性与防重放机制

- 请求头固定、可被完整仿造；
- 没有请求签名（HMAC）、时间戳、nonce 防重放、设备指纹等任何一项，
  导致外部脚本可以无门槛地直接调用上报接口。

### 根因 4：异常运动模式缺乏风控

- 脚本产生的轨迹"过于完美"（等距点位、方差极小的配速、机械化的上传节奏），
  在缺乏服务端异常检测的情况下不会触发任何告警。

### 根因 5：小程序包（wxapkg）使用已知固定盐 / IV 的弱加密

- 解包使用固定盐 `saltiest`、固定 IV，以及末位字符异或，属于公开可破解算法，
  任何人都能解包拿到接口路径与业务逻辑。
- 这说明：**不能把安全寄托在"客户端代码保密"上**，必须在服务端兜底。

## 三、修复建议（按优先级分层）

### A. 服务端侧运动校验（最高优先级，根治方向）

- **不信任客户端上报的里程 / 配速**：服务端应基于上报的**原始 GPS 轨迹自行计算**里程、
  配速、加速度，并做物理合理性检验：
  - 相邻点速度 / 加速度上限校验；
  - 定位精度（`accuracy` / `horizontalAccuracy`）分布是否符合真实手机 GPS
    （真实数据有抖动、丢点、漂移，脚本通常过于规整）；
  - 轨迹是否过度规则（等距点、围栏内缩的同心环形应判为异常）。
- **围栏校验升级**：从"点在多边形内"升级为"轨迹是否贴合真实可跑路径（操场跑道 / 校园道路）"，
  纯几何内缩的环形轨迹应被识别并拒绝。
- **步数交叉校验**：步数应取微信运动 `WeRunData`（后端用 `session_key` 解密验签）而非
  客户端裸报，并与里程 / 配速做步频合理性交叉校验。

### B. 凭证安全

- `au` 改为**短时效 + 滑动过期**，并与**设备指纹 + openid + IP 段**绑定，异端 / 异地使用即失效；
- 关键接口要求微信侧二次校验（`code2session` 换 session，后端校验 openid），
  不让单一长效凭证独立决定身份；
- 前端尽量不下发 / 不长期保留 `sessionKey` 等明文敏感字段，减少内存提取面。

### C. 请求完整性与防重放

- 运动上报接口加入**请求签名**：`HMAC(body + 时间戳 + nonce, 会话密钥)`，
  服务端校验签名 + 时间窗 + nonce 去重，阻断外部 HTTP 客户端的直接重放；
- 强制 TLS 并做证书校验，抬高纯脚本仿造门槛。

### D. 打卡照片真实性

- 打卡照片要求来自实时摄像头（水印 / 拍摄时间 / 最低限度的真实性证据），
  至少检测并拒绝纯程序生成的噪声图，并与运动时间 / 地点做一致性校验。

### E. 风控与审计

- 建立服务端异常检测：同一账号短时间多次完成、配速方差极小、上传节奏机械化、
  UA / IP 异常等，触发人工复核或自动作废；
- 对每次运动全过程留痕，便于事后审计与回溯。

### F. 客户端加固（辅助手段，非根治）

- 升级 wxapkg 加密与代码混淆，将关键判定逻辑后移到服务端；
- 必须明确：**客户端始终不可信，安全的最终防线一定在服务端。**

## 四、结论

本漏洞的本质是**服务端过度信任客户端上报的运动数据，且会话凭证可被提取重放**。
最有效、最根本的修复方向是 **A（服务端独立计算与合理性 / 真实性校验）+ C（请求签名防重放）**；
其余措施用于收敛攻击面与提升作弊成本。建议优先落地 A、C，再逐步完善 B、D、E。

如需，作者愿配合校方进一步复现、验证与联调修复效果。
