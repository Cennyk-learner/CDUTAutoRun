## 一、项目简介

这是一次针对**成都理工大学"校园跑 / 体育打卡"微信小程序**（后端 `clty.cdut.edu.cn`）的
安全漏洞研究记录。研究发现：在**完全没有真实运动**的情况下，可以通过脚本伪造一段 GPS 轨迹，
使服务端记录下一次**合规且达标**的校园跑。

本仓库的目的：

- 向校方清晰说明漏洞的**根因**与**利用链**；
- 给出可落地的**修复建议**（见 [docs/漏洞分析与修复建议.md](docs/漏洞分析与修复建议.md)）；
- 作为一次完整安全研究过程的**技术记录**。

> 本仓库已移除全部个人敏感信息（姓名、学号、班级、userId、sessionKey、会话 token、
> 文件访问 URL 等）与进程内存转储、反编译出的小程序源码，仅保留研究方法与脱敏后的演示。

## 二、漏洞概述

| 项 | 说明 |
| --- | --- |
| 影响系统 | 校园跑 / 体育打卡微信小程序及其后端接口 |
| 漏洞类型 | 客户端数据被过度信任 + 会话凭证可提取重放 + 缺乏防重放/风控 |
| 利用前提 | 在**本人账号、本人授权**的电脑微信上提取本人会话凭证 |
| 利用效果 | 无真实运动即可生成一次达标的校园跑记录 |
| 根本原因 | 服务端几乎完全信任客户端上报的里程/配速/步数/GPS，且无服务器侧独立校验 |

利用链（高层）：

1. **提取会话凭证**：从电脑微信小程序进程内存中读出服务端校验身份的 `au` 字段；
2. **读取规则**：调用规则接口拿到里程、配速、时间窗、地理围栏多边形等要求；
3. **构造轨迹**：在地理围栏内（按比例内缩）生成一条满足里程/配速要求的环形轨迹；
4. **按真实耗时上报**：模拟 start → 多次 gps 上报 → end，并上传一张占位"打卡照片"；
5. **服务端记录达标**：最终生成一条"有效"的运动记录。

> 脱敏后的演示日志见 [samples/run_once.sample.log](samples/run_once.sample.log)。

## 四、运行说明（仅限授权的安全研究环境）

> 仅可在**本人账号、本人授权**的环境中用于验证与研究，**禁止**针对他人账号或用于任何真实作弊。

- 先只检查能否提取并校验本人凭证（不产生任何运动记录）：

  ```bash
  py -3.12 auto_au.py
  ```

- 仅生成计划、不真正上报（dry-run，强烈建议研究时只用这一步）：

  ```bash
  py -3.12 run_once.py --dry-run
  ```

`run_once.py` 默认会真实走完整个上报流程；本仓库保留它是为了向校方**完整、可信地说明问题**，
请勿将其用于任何非授权或非法目的。

## 五、修复建议（摘要）

最根本的方向是让**服务端不再信任客户端上报的运动数据**：

- **服务端独立校验**：基于原始 GPS 轨迹自行计算里程/配速，并做物理合理性与真实性检验；
- **围栏升级**：从"点在多边形内"升级为"轨迹贴合真实可跑路径"，识别几何内缩的环形轨迹；
- **凭证安全**：`au` 短时效 + 设备/会话绑定，关键接口结合微信侧二次校验；
- **请求签名防重放**：`HMAC(body+时间戳+nonce, 会话密钥)` + nonce 去重；
- **打卡照片真实性校验 + 异常风控审计**。

完整方案见 **[docs/漏洞分析与修复建议.md](docs/漏洞分析与修复建议.md)**。
